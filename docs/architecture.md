# 架构与完整链路

目标是用一个 Next.js 应用、一个 PostgreSQL 数据库，连接 HR 的一句话与真实招聘数据。页面、服务端 API 和业务模块位于同一工程；没有独立消息队列、向量数据库或多 Agent 编排。

## 查询

```text
HR 提问
→ 本地识别意图、姓名、岗位和日期
→ 在服务端查找实际档案或面试安排
→ 数据不足时澄清
→ 根据查询结果生成回答
```

查询不会修改候选人。助手输出的业务事实由数据库提供，规则识别器只决定查什么。

## 流程推进

```text
HR 描述招聘进展
→ 提取候选人、目标阶段或面试安排
→ 根据当前对话补全缺失信息
→ 解析唯一档案；同名或不存在时澄清
→ 保存待确认操作及档案版本
→ 展示变更卡
→ HR 确认
→ 检查操作状态、有效期与档案版本
→ 在同一事务内写档案、面试与操作记录
```

用户可以取消待确认操作。创建操作卡不等于已经安排面试，页面不能提前显示成功。重复确认也不能重复创建同一场面试。进程中断后的自动任务恢复不在此版范围内；这里没有承诺后台自主执行。

## 简历录入

```text
上传文件或粘贴文本
→ 文件类型、大小和文本长度检查
→ 提取文本并保留 PDF 字段换行
→ 本地规则抽取基本字段
→ HR 核对并修改
→ 选择岗位，查看技能关键词提示
→ 保存档案、原文、原文件与入库记录
```

未知字段保持为空。没有调用外部模型，也没有模型生成的匹配评分或校准置信度。

## 数据对象

| 对象 | 职责 |
|---|---|
| jobs | 岗位标题、JD 与关键技能 |
| candidates | 某次应聘的资料、招聘阶段、后续动作与原件 |
| interviews | 该档案的面试轮次、日期、时间、面试官与地点 |
| activities | 已确认生效的业务操作 |
| pending_actions | 待确认变更、有效期、执行状态与预期档案版本 |

简历原件限定为小文件，用 PostgreSQL BYTEA 和资料放在同一数据库中，降低作品版部署和备份的复杂度。后续有大文件需求时，再评估独立文件存储。连接使用 pg 连接池；确认操作在同一客户端事务内完成。

`pnpm db:init` 显式执行 `db/schema.sql` 和 `db/seed.sql`，运行期不自动建表或重新填入演示资料。可以连接已有 PostgreSQL，也可以使用 `docker-compose.yml` 中的单数据库容器。

## 扩展入口

意图识别集中在 `src/server/intent.ts`，输出 `ParsedIntent`，由业务层执行查询或构造操作卡。未来即使改用大模型，也只替换识别入口；候选人查找、有效性检查、人工确认和事务写入仍由服务端掌握。

此版不添加空的框架层或不可用的第三方接入。新增能力应围绕明确的 HR 操作扩展意图和业务处理，而不是增加一套独立服务。

本轮按用户要求只搭建代码，没有执行运行验证；具体行为仍需之后验收。
